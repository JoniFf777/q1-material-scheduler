# 项目复盘

本复盘由 Codex 根据项目中实际出现的问题、修正和验证结果协助归纳。它总结工程过程；候选人的实际操作与 AI 辅助范围见 [AI 使用记录](04-ai-usage.md)。

## 最难的问题：让评估适配模型实际动作

最有代表性的问题出现在真实模型评估，而非离线流程中。S09 限制最多 4 轮调用，生成的场景却固定要求 M07 为 unknown。Mock 脚本逐个读取素材，在 4 轮内没有审核 M07，所以该断言一直通过。

真实模型会在一轮中发出多个工具调用。它先批量读取和审核，再补查 M04、M07 的授权；到第 4 轮结束时，M07 已审核通过。系统正确返回 `incomplete`、`MAX_STEPS_REACHED` 和 `not_saved`，评估器仍将结果判错，形成最初的 30/33。

定位时对照了规格、Trace 中的工具返回和实际输出。规格要求“未处理的素材为 unknown”，并未固定哪一个素材不能处理。最终修正评估器与生成场景，按本次运行的审核事实验证未处理条目，保留限额和未保存要求，并增加批量调用回归。回归测试先复现失败，修正后通过；重新真实调用得到 33/33。[原始失败与修正说明](03-evaluation.md) 均保留在仓库中。

这说明固定 Mock 可以覆盖执行机制，却容易把脚本的动作顺序误当作模型必须遵守的行为。评估应约束业务结果和安全边界，允许模型选择不同的合法动作组合。

## 另一个关键难点：重复请求与确认边界

同一请求第二次执行时，原草稿已经占据建议时段。如果查询把自身草稿也当成外部冲突，模型可能不断向后挪动时间。实现将自身占用标为 `held_by_this_request`，外部排期与自身旧草稿重叠时仍以 `occupied` 为准；保存冲突校验排除本请求旧版本。S04→S06→S06b 实际验证了 created v1→duplicate v1→updated v2，草稿始终一份。

确认也需要区分两个维度：审核通过不等于排期已经确认。候选人手动 S04 的真实 Trace 中，模型曾把时间调整待确认写成审核 needs_confirmation。代码拒绝了这次保存，模型根据错误返回修正。`confirmed` 则只能来自结构化用户答复，保存时检查具体素材、确认类型和提议时间，模型自己的说法不能代替用户输入。

## 主要收获

- 将模型的建议与业务事实分开：模型决定查什么、是否补查和如何处理冲突；代码验证硬约束、确认来源、保存结果和幂等性。
- 用真实工具错误验证闭环：校验错误返回给模型后，模型修正下一次动作，是可观察的决策证据。最终结果应由事实账本组装。
- 评估同时关注结果与边界：成功用例的输出、保存失败的真实状态、限额后的未完成状态都需要验证，达到上限不等于越权完成。
- 新克隆验证能暴露本地环境掩盖的问题：原目录已有 runtime，使缺失的安装步骤未被发现；独立环境才暴露这一点。
- 保留失败比只留最终通过更有解释力：本仓库同时记录初始评估、回归测试与重新运行结果，便于说明修正依据。

## 下一步改进

1. 增加真实模型样本与输入变体，覆盖拒绝确认、多个素材争抢时段、授权变化和更换占用位置，并比较另一家模型的成功率、轮数与 token 用量。
2. 收紧报告字段的格式说明，减少模型在时间字段中混入渠道等文字造成的纠正提醒，同时保留代码校验。
3. 将 JSON 存储升级为数据库事务，为请求幂等键与渠道时段建立唯一约束，解决跨进程并发问题。
4. 对用户确认接入身份、权限与审计，并增加可恢复的交互确认入口。当前文件输入被视为可信用户输入。

当前 CLI、整点时段和单进程存储满足本题核心链路；真实素材服务、终端交互和多用户并发仍属于后续工作。模型在本次有限样本中通过全部场景，不代表任意输入都能在限额内完成。
