# 01 题目拆解

## 1. 一句话目标

内容团队提交"要排期的素材 + 发布时间要求"。Agent 逐个审核素材、查时段、处理冲突，产出一份**无冲突、可确认的排期草稿**。只存草稿，不发布。

## 2. 题目要素 → 设计落点

| 题目原文 | 设计落点 |
|---|---|
| 找出待处理素材 | `list_pending_materials` 工具；请求可以直接给 ID，也可以写 `scope: "pending"` |
| 素材读取 / 规则检查 / 时段查询 / 草稿保存 | 对应 `get_material` / `check_rules` / `query_slots` / `save_schedule_draft` |
| 补查 | `get_material(detail="full")` 读扩展元数据；`check_rules(scope="license"\|"content")` 做深度检查 |
| 替代时段 | 模型用 `query_slots` 查附近窗口，在硬性约束内选替代时段，并标记待确认 |
| 请求确认 | `request_confirmation` 工具：登记待确认项，交互模式下可当场问用户 |
| 阻断 | 素材标为 `blocked`，不分配时段，草稿里写明原因 |
| 不得擅自改变硬性发布要求 | 请求里显式区分硬约束和软偏好；`save_schedule_draft` 在代码层校验，违反就拒绝 |
| 每项素材的交付字段 | 最终结果按素材输出：审核状态、风险原因、建议时段、待确认项、草稿保存状态 |

## 3. 必须验收点（6 个）

| # | 验收点 | 正确行为 | 场景 |
|---|---|---|---|
| A1 | 正常排期 | 无风险、时段空闲 → 按要求排期，草稿 `created` | S01 |
| A2 | 素材信息缺失 | 先补查；仍缺 → `need_info`，不排期，列出要补什么 | S02 |
| A3 | 规则风险 | 硬风险 → `blocked`；软风险 → 请求确认；不确定 → 补查后再定 | S03 |
| A4 | 时段冲突 | 软偏好 → 给替代时段并标待确认；硬要求 → 不改，请求用户决定 | S04、S05 |
| A5 | 重复提交 | 同一请求再提交，草稿总数不变，返回 `duplicate`；时段数据变了就 `updated` 升版本 | S06 |
| A6 | 保存失败 | 明确返回失败和错误码，草稿文件不变，绝不说保存成功 | S07 |

通用要求另外覆盖：工具失败（S07、S08）、步数上限（S09）、至少两条执行路径（S01 对 S04，S03 里 M04 对 M07）。

## 4. 参考实例的精确语义（必须逐字满足）

> M01 无风险，用户要 18:00，该时段已占用、19:00 可用 → 建议 19:00 并标记待确认；不得称为已发布。

- `suggested_slot = 19:00`，`slot_status = alternative`，`confirmation_status = pending`
- `pending_confirmations` 里有一条 `time_change`，问题里写明"18:00 被谁占用、是否改到 19:00"
- 草稿保存成功的说法是"草稿已保存（待确认，未发布）"
- 18:00 是**软偏好**，所以才允许提出替代时段；如果是硬要求，见 S05

## 5. 红线（评审说的"关键缺陷"）

| 红线 | 防线（代码层，不只靠提示词） |
|---|---|
| 越权发布 | 没有发布工具；状态枚举里没有 published；输出文本过滤"已发布/发布成功"等说法 |
| 虚报保存成功 | 最终结果的保存状态由代码从工具执行记录里取；与模型说法不一致时以记录为准，并记一条 warning |
| 擅改硬性要求 | `save_schedule_draft` 校验硬约束，违反就返回 `HARD_CONSTRAINT_VIOLATION` |
| 未确认就当确认 | 时段与请求不一致的条目，必须是 `pending`；只有用户确认输入才能变成 `confirmed` |
| 重复草稿 | 幂等键由代码计算；同一个键只能对应一份草稿 |
| 跳过审核直接排期 | 本次运行里没跑过 `check_rules` 的素材，保存时直接拒绝 |

## 6. 硬约束 vs 软偏好（本题最容易做浅的地方）

请求里每个素材的时间要求拆成两部分：

```json
"preferred_time": "2026-11-10T18:00",
"time_policy": "flexible",
"constraints": { "date_fixed": true, "not_after": "21:00", "channel_fixed": true }
```

- `time_policy: "fixed"`：时间本身就是硬要求，不能改。冲突了只能请求确认或阻断。
- `flexible`：可以在 `constraints` 范围内找替代时段，但必须标待确认。
- 不论哪种，`constraints` 都是硬约束。要放宽只能由用户确认。

## 7. 范围

**做**：CLI；6 个工具（本地函数加合成数据）；真实模型加 Mock 两种模式；JSON 草稿存储；Trace 记录；pytest；10 个示例场景。

**不做**（写进限制说明）：真实发布、真实素材系统、多用户并发锁、Web 界面、多 Agent、自然语言请求解析（输入用结构化 JSON，`note` 字段可以写补充说明）。

## 8. 成功标准

- 6 个验收点在 live 模式下都有输入、输出、Trace，并且符合第 3 节的正确行为
- 红线相关的单元测试全部通过（离线可跑）
- 每个场景用 live 跑 3 次，记录通过率（衡量模型的稳定性，写进 03-evaluation）
